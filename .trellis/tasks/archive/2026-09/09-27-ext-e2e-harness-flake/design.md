# Design: 脚手架假红源的三类机制

## 1. 三类假红源（机制各异，修法各异）

| 类 | 机制 | 为什么难察觉 | 本片修法 |
| :--- | :--- | :--- | :--- |
| **裸异常打断等待** | `documentElement` 在 `<html>` 创建前为 `null`，`.classList` 抛 TypeError；它从 `waitFor` 的回调里抛出去 → 整轮等待被**打断**，而不是「再试一次」 | 失败文案是 `Cannot read properties of null`，看起来像产品崩了 | 空值守卫 → 表达为「尚未就绪」，交给 `waitFor` 重试 |
| **掩盖层** | `p.then(断言…).catch(() => assert.fail('init() should not reject'))` —— `.catch` 也会接住 `.then` 里的断言失败 | 报出的话**与事实相反**（init 并没 reject），把诊断带偏 | 失败信息带出真实 `e.message` |
| **固定等待是概率** | `setTimeout(…, 40)` 等分片写链（十几次串行 1ms mock 往返）落盘 | 机器一忙就丢；且概率随负载变化，重跑即绿 → 被当成「偶发」放过 | 有界轮询（`pollUntil`）等**状态**而不是等时长 |

## 2. 为什么用 `pollUntil` 而不是加长固定等待

项目已有结论（journal）：**固定等待是概率、不是时长**；把 30ms 加到 300ms 仍是偶发，
因为正确性依赖「本文件同步执行时间 + 全局负载不越过该值」，而每加一个断言块都在往下压。
`pollUntil` 的既有契约正好满足需求：条件满足即走（绿路径更快），超时后**走同一组断言**
（真实缺陷照样报红，不吞失败），且受 `ASYNC_POLL_MS` 与收尾台账自检约束。

## 3. 有界轮询的谓词要取「断言依赖的完整状态」

H2 的谓词不是「有没有 `.meta`」，而是「**能不能重组成一个 `brightness=0.77` 的 `svi:prefs`**」——
分片写的中间态是「meta 已落、chunk 未齐」，只判 meta 会把抖动从一条断言挪到下一条。

## 4. 测量口径（本片确立，防「假绿」与「误判回归」）

门禁汇报必须三分：**真红**（点名断言） / **SKIP 未验证**（`SKIP: 未验证 (CDP 未就绪)`，
文档化降级路径、exit 0） / **基础设施抖动**（`CDP 超时`、`等待超时: 探针攒够 60 帧`）。
三者混算会同时造成两类错误：把 skip 当绿（掩盖未覆盖），把抖动当回归（误伤产品）。

## 5. 残留抖动清单（不在本片承诺清零）

| 现象 | 归属 | 备注 |
| :--- | :--- | :--- |
| `CDP 超时 (Runtime.enable))` | 基础设施 | Chrome/CDP 未就绪或目标已关 |
| `等待超时: 复访: 探针攒够 60 帧` | rAF 停滞 | AGENTS.md 已记：occluded/hidden 窗口 rAF 掉到 ~1 帧/500ms；需三枚禁用节流的 flag + `Page.bringToFront` |
| `内容脚本页卸载时的整份回写不得把设…` | 场景 8 竞态 | 跨界面同步用例，同步防抖写 |
| `清除后快照的覆盖站点数应归零` | 站点重置用例 | 同上族 |

共同族：**用固定等待同步防抖/分片写**。系统性收敛（把这类等待全换成有界轮询）属另一片，
本片只修掉两处已定位、影响面最大的（H1/H2）并确立口径。

## 6. 验证与回滚

验证：`test.js` 连跑 5 次（基线 2/5 → 5/5）；`test-extension` 的 `classList` 类归零（3/6 → 0）；
`test-browser` 33 场景（3 次连跑全过）。回滚：纯测试改动，`git revert` 即可，无产品影响。
