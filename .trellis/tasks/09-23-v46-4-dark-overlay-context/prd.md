# v4.6-4 暗色遮罩容器场景的错误反色

## Goal

个人主页等场景父容器有暗色遮罩/蒙层, 视觉已暗但原图偏亮, 导致脚本按原图亮度误判反色; 需引入祖先遮罩上下文判定。

## Requirements

### 用户原话

> 「复杂场景：如个人主页显示的地方，可能会加上暗色遮罩，会使视觉还好，但是原图是亮的，
> 导致新的一种错误反色」

### 场景解释（实施者须先确认该解释，不符则回写 prd）

容器（如个人主页头图区）上覆盖了一层**半透明暗色蒙层 / 渐变遮罩**：最终**合成渲染结果偏暗**
（视觉上已经"够黑"，不需要处理），但被覆盖的图片**自身的像素是亮的**。脚本若只按
"图片自身像素亮"判定 → 反色 → 得到一张亮图叠在暗蒙层上，**合成后反而变亮/发灰**，形成
与常规相反的错误。这就是「新的一种错误反色」。

### 需求

- **R1 祖先遮罩感知**：判定子媒体时须考虑**祖先链上的暗色遮罩/蒙层**（半透明黑背景、
  线性/径向渐变遮罩、`::after`/`::before` 覆盖层、`mix-blend-mode`、`background-blend-mode`、
  `backdrop-filter`、`opacity` 叠加等可本地检测的形态）。
- **R2 合成优先**：当祖先遮罩使**可见合成结果**已足够暗时，不得再对该媒体执行反色
  （应判 `keep` 并打可审计标记，如 `data-svi-reason="masked-dark"`）。
- **R3 本地可得**：遮罩检测必须基于本地可得的样式信息（`getComputedStyle` / 祖先遍历 /
  元素的几何覆盖关系），不得引入网络依赖，不得为此增加显著性能开销
  （须有预算：如只检查有限层数祖先，且结果缓存进决策快照）。
- **R4 不误伤**：
  - 浅色蒙层（如白色半透明）不得触发本规则；
  - 真需要反色的亮图（无遮罩）行为不变；
  - 遮罩下仍明显偏亮的合成结果应仍按常规判定。
- **R5 可解释**：新增判定原因标识，配合面板/统计可见，便于后续排查。
- **R6 decide-once 兼容**：遮罩判定结果纳入决策快照，同输入不翻转。

## Acceptance Criteria

- [ ] 本地 fixture 页面：构造 4 个对照元素（亮图+暗蒙层 / 亮图+无蒙层 / 亮图+浅蒙层 /
      暗图+暗蒙层），断言分别得到 keep-masked / invert / invert / keep
- [ ] 真站证据：至少 1 个个人主页类站点（如 GitHub 用户主页头图区、B站空间页、掘金个人主页）截图 + 决策报告
- [ ] 遮罩检测的性能预算证据（处理时间开销可接受，无长任务）
- [ ] 判定原因在决策报告/统计中可读（非仅内部属性）
- [ ] 5 次重载稳态一致（decide-once 不被破坏）
- [ ] 四绿门禁全绿
- [ ] 结论写回 `.trellis/spec/frontend/quality-guidelines.md`

## Notes

- 本任务是**新增判定能力**，风险最高：必须避免"把大量正常反色判成 keep"。
  建议做法：先只处理"明确形态"（祖先存在半透明深色覆盖层且覆盖率 ≥ 阈值），
  留出保守开关与统计计数，观察一轮再放宽。
- 与子任务 1 的交集：若 1 的二分结论表明本场景是被某个"本地优先"改动引入/放大的，需交叉引用。
- 背景替换引擎（bgr）与图片引擎都可能命中此场景，两处都要覆盖。
