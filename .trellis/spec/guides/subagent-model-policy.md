# 子代理与派发模型策略（强制）

> **适用范围**：本项目（以及任何使用 Trellis 的项目）中，主代理向任何子代理 / channel worker
> 派发任务之前。违反本策略的派发视为无效派发。
>
> **来源**：用户 2026-09-23 明令。原文：
> 「需要你来编排规划任务，然后派发代理并行做（主代理不等待），必须询问子代理使用什么模型，
> 然后才能继续使用 glm5.3flash（注意，所有的模型名都不是全称，必须选择最匹配，询问，
> 禁止当成正确名字）。」

---

## 一、八条铁律

### 1. 派发前必问模型

任何子代理 / channel worker 派发**之前**，必须先向用户询问"用哪个模型"并得到确认；
**确认之后**才允许执行派发命令。

- 禁止用主代理当前模型静默派发。
- 禁止以"用户没回话所以用默认值"为由跳过询问。
- 一次会话内已就同一模型确认过的，可复用该确认（在会话中显式声明"沿用 X 确认"），
  但**不得跨会话**默认为已知。

### 2. 模型名一律不视为全称

用户给出的模型名（如 `glm5.3flash`）、历史记录里的模型名、文档里的模型名，
**一律视为不完整 / 近似 / 可能拼错**。

流程固定为：

1. 在**平台实际可用清单**中检索最匹配的候选（多个候选就都列出来）；
2. 把候选 + 推荐理由呈给用户；
3. 用户点选确认后，才把该字符串写进派发命令。

**禁止**把近似名直接当成正确名使用。**禁止**静默"纠正"成自己认为对的名字。

### 3. 已确认默认值

本项目当前**已确认**的子代理默认模型为：

```
GLM-5.3 Flash
```

确认记录：2026-09-23，用户交互问答中点选（候选项来自平台清单，非用户原始输入的
`glm5.3flash`）。该字符串是"当前默认值"，**不是**"可以静默使用的免询问牌照"。

### 4. 能力档位：子代理要便宜

子代理承担的是"读多写少"的检索 / 提炼 / 核验工作：

- 选平台清单中**能力最低档且最匹配任务**的模型；
- 旗舰 / 高能力模型留给主脑做判断与集成；
- 询问用户时应主动给出"最低档候选"，而不是默认推荐最强模型。

### 5. 禁用项

- **禁止使用 `Kimi K3` 做子代理**（用户 2026-09-21 明令，长期有效）。

### 6. 「主代理不等待」= 后台 worker，不是阻塞式子代理

| 机制 | 是否真并行 | 适用 |
|---|---|---|
| `trellis channel spawn ... --model <已确认模型>` | ✅ 真并行，主代理不阻塞 | 用户要求"并行做 / 不等待"时必须用这个 |
| 阻塞式子代理调用（如 VS Code `runSubagent`） | ❌ 主代理必须等结果 | 只读调研、串行验证；**不得**用来冒充"并行" |

用阻塞式调用冒充并行 = 违反本策略。

### 7. 派发上下文铁律

每次派发 prompt 的**首行**必须是：

```
Active task: <task.py current 输出的任务路径>
```

其后才是角色指令。缺少该行视为无效派发。

### 8. 派发必须自包含

子代理没有共享记忆，派发 prompt 必须自带：

- 检索 / 修改范围（具体路径、具体函数）；
- 具体问题或验收标准；
- 期望产出（文件路径 + 格式）；
- 明确"只读调研"还是"允许写代码"。

## 二、标准派发流程

```text
1. 规划任务（Trellis 任务树：父任务 + 可独立验收的子任务）
2. 【必问】向用户询问子代理模型 → 列最匹配候选 + 推荐 → 等用户确认
3. 记录确认（会话中显式声明；必要时写入任务 notes）
4. task.py start <子任务>            # 状态 → in_progress
5. 派发（首行 Active task: ...）
   - 需要并行不等待 → trellis channel spawn <ch> --agent implement \
        --as <worker> --cwd <repo> --model "<已确认模型>" \
        --file <prd.md> --file <design.md> --file <implement.md> \
        --jsonl <implement.jsonl> --timeout 30m
   - 再把任务描述经 trellis channel send 送入 worker
6. 主代理继续做自己的事（不等待）；收集 worker 的 done/error 事件
7. 全部完成后：交叉核查 → 集成 → 四绿门禁 → 统一 commit + push
```

## 三、反例清单（出现任一即违规）

- ❌ 没问用户就直接 `spawn` / 调子代理。
- ❌ 把用户写的近似模型名（`glm5.3flash`、`glm5.3`、`deepseek v4 flash`）当成正确名写进命令。
- ❌ 用 `runSubagent` 之类阻塞调用，却对用户宣称"已并行派发、主代理不用等"。
- ❌ 子代理用旗舰模型跑"读文件 + 总结"这类低能力任务。
- ❌ 使用 `Kimi K3` 做子代理。
- ❌ 派发 prompt 缺 `Active task: <path>` 首行。
- ❌ 派发 prompt 不含具体范围/问题/产出，指望子代理"自己猜"。

## 四、两个通道的模型 ID 空间不同（2026-09-23 实测）

“模型名不是全称”这件事在**不同派发通道上表现不同**，必须分别取精确串：

| 通道 | 名称来源 | `glm5.3flash` 对应的**精确串** | 实测 |
|---|---|---|---|
| VS Code / Copilot 子代理 | 模型选择器显示名 + 厂商 | `GLM-5.3 Flash (unify-chat-provider)` | 平台接受 |
| | （错误尝试） | `GLM-5.3 Flash (copilot)` / `GLM-5.3 Flash` | ❌ 平台拒绝：model not found |
| Trellis channel worker（claude CLI） | 本地代理 `127.0.0.1:15721/v1/models` 的 slug，或 `~/.claude/settings.json` 里的别名 | `glm-5.3-flash` 或别名 `claude-sonnet-5[1M]` | ✅ 代理 HTTP 200（分别 49.7s / 21.4s） |
| | （错误尝试） | `GLM-5.3 Flash` | ❌ CLI 报 `unrecognized_model`，代理回 502 |

经验规则：

1. **先定通道，再取 ID**。Copilot 子代理填“显示名 (厂商)”；claude CLI / 代理填 slug 或 settings 别名。
2. **厂商后缀不能省也不能猜**：`(copilot)` 与 `(unify-chat-provider)` 是不同厂商空间，填错直接失败。
3. **获取清单的可靠方式**：Copilot 侧拿不到清单时，故意发一次不合法的 `model` —— 平台会在错误
   信息里列出全部可用模型；代理侧则直接 `GET /v1/models`（本机实测返回 9 个模型）。
4. **连通性先验证再派发**：对代理直接发一次极小请求（`max_tokens: 4`）确认 200，避免 worker 陷入
   502 重试风暴（本次实测：4 个 worker 同时重试 10 次，白烧额度）。
5. 本项目已确认的**默认选择**：Copilot 子代理用 `GLM-5.3 Flash (unify-chat-provider)`；
   channel worker 用 `glm-5.3-flash`（或别名 `claude-sonnet-5[1M]`）。

## 五、维护提示

- `.trellis/agents/implement.md`、`.trellis/agents/check.md` 的 frontmatter `model` 字段
  是本策略的落地载体，但这两个文件由 Trellis 生成/维护：
  **每次 `trellis update` 之后必须复核该字段是否仍在**，被覆盖则重新补上。
- `.github/copilot-instructions.md` 与 `AGENTS.md` 内的 Trellis 标记块属生成物，
  本策略内容必须写在**标记块之外**，否则会被下次生成覆盖。
- 若上游 Trellis 开始原生支持"派发前询问模型"，应把本策略迁移为上游配置，而不是继续本地打补丁。

## 六、编排自主权：收尾类动作不问，冲突才问

> **来源**：用户 2026-09-24 明令。原文：
> 「这些不用问，你编排，这个写入规则，除非有冲突」。

### 6.1 默认自主

主代理对以下**收尾类 / 低风险 / 可逆**动作**自行编排并直接执行**，
不得为逐条征询而打断用户：

- 补齐文档（README / README_EN / 任务笔记）与版本号同步；
- 回填任务 PRD / implement 的验收勾选与结论；
- 清理已归档任务的重复副本、已注销的 worktree 残留、临时产物；
- 归档、日志、spec 沉淀、四绿门禁重跑；
- 按已确认方案继续未完成的实现步骤。

判定口径：**做错了也只是返工、不会造成不可逆损失**的动作 → 自主执行。

### 6.2 例外：必须停下询问

出现以下任一情形，**必须立即停下并征询用户**，不得自行拍板：

| 情形 | 为何要问 |
|---|---|
| **冲突**：验收标准与实测数据不符、子任务结论互相矛盾、规则与规则打架 | 需要用户裁决取舍，主代理无权单方面放宽或修改验收标准 |
| **不可逆**：删除/覆盖已有文件、丢弃未提交改动、重写历史、清理分支 | 影响不可回收 |
| **环境变更**：安装依赖、改全局配置、动代理/网络设置 | 影响面超出本仓库 |
| **方向性取舍**：架构方案二选一、重构 vs 重写、技术选型 | 影响项目走向，须用户选定 |
| **超出范围**：发现的问题需要扩大改动面才能修 | 范围变更应由用户决定 |

### 6.3 组合执行

自主执行时，把同批可做的收尾项**一次性编排完并汇报结果**，
而不是每做完一件就回来问一次"下一件做什么"。汇报时给出：
做了什么、证据（命令/行号/实测数据）、遗留什么。

### 6.4 与其他规则的关系

- 本节**不豁免**第五节之外的安全规则：`CyberDomain PARDON` 治理铁律（全局规则 §6）
  仍然有效——「删除/覆盖文件」「安装包」等**不可逆**动作依旧必须显式确认。
- 本节与 6.1 的"清理残留"不冲突：清理**未被任何提交引用的临时残留**属自主范围；
  删除**已跟踪的正式文件**仍走询问。
